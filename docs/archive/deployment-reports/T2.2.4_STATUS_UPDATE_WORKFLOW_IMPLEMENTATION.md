## Status State Machine

```
┌──────┐
│ sent │ (initial state when vendor request created)
└──┬───┘
   │ (automatic on first view)
   ↓
┌────────┐
│ opened │ → Show SchedulingForm
└────┬───┘
     │ (when scheduled_date + scheduled_time provided)
     ↓
┌───────────┐
│ scheduled │ → Show CompletionForm + scheduled date/time
└─────┬─────┘
      │ (when completion_notes provided)
      ↓
┌───────────┐
│ completed │ → Show success message + completion notes
└───────────┘ (final state)

Alternative terminal states:
┌─────────┐
│ expired │ → Show expired message
└─────────┘

┌───────────┐
│ cancelled │ → Show cancelled message
└───────────┘
```

## Form Submission Flow

### Scheduling Flow:
1. User selects future date and time
2. Click "Schedule Appointment" button
3. Client validates date is in future
4. Show loading spinner on button
5. Call `vendorService.updateVendorRequest(token, { scheduled_date, scheduled_time })`
6. On success:
   - Show success toast: "Appointment scheduled successfully!"
   - Refresh vendor request data
   - Parent callback `onScheduled()` triggers re-render
   - UI automatically switches to CompletionForm
7. On error:
   - Show error toast with specific message
   - Keep form open for retry
   - Form remains editable

### Completion Flow:
1. User enters completion notes (minimum 10 characters)
2. User optionally uploads document via integrated DocumentUpload
3. Click "Mark as Completed" button
4. Show confirmation dialog with warning
5. On user confirms:
   - Show loading spinner
   - Call `vendorService.updateVendorRequest(token, { completion_notes, document_url })`
   - On success:
     - Show success toast: "Task marked as completed successfully!"
     - Refresh vendor request data
     - Parent callback `onCompleted()` triggers re-render
     - UI shows completed state with green success message
   - On error:
     - Show error toast
     - Keep form open for retry
6. On user cancels:
   - Close dialog
   - Return to form
